# MyGolf 基本設計（案）

作成: 2026-11-15 ／ 根拠文書: 「新スコアアプリ_要件定義_案.md」（追補4をもって凍結）
位置づけ: 実装に入る前の基本設計。詳細な画面仕様・GAS 実装仕様は本書を起点に詰める。

---

## 1. 全体構成

```
[iPhone: MyGolf PWA] ──HTTPS── [GAS Web アプリ（新規・検証用コピー紐づき）] ── [マイスコア_DB_新アプリ検証用]
        │ ローカル保存: IndexedDB（正）／クラウド下書きは復旧用の副
        ▼ ラウンド後
[Muse 後処理] FIT（Venu X1）＋ DB コピーを読み、Review＋ショットマップを生成
```

- オリジン: https://osa6ku.github.io/MyGolf/ （固定。変更しない）
- DB は検証用コピーが正。本番 DB には一切触れない
- 分析・レビューはアプリに持たず、完全後処理（U-11）

## 2. クライアント構成（ES モジュール、ビルドなし）

| モジュール | 責務 |
|---|---|
| `main.js` | 起動、画面遷移、Service Worker 登録 |
| `db.js` | IndexedDB の薄いラッパー（読み書き＋読み戻し照合） |
| `state.js` | 進行中ラウンドの状態管理（単一の真実。画面は state を描くだけ） |
| `master.js` | コースマスタの取得・キャッシュ・検索 |
| `sync.js` | GAS クライアント（下書き保存・取得、確定保存、保留キュー） |
| `ui-setup.js` | ラウンド設定（コース・条件・同伴者・ゲーム設定・端末間復元オプション） |
| `ui-hole.js` | ホール入力（本人＋同伴者、番手、メモ、合計表示） |
| `ui-restore.js` | 復元画面（「無い／不完全」の分離、概要提示、世代選択） |
| `game.js` | トモダチゲーム計算、打順シャッフル／手動設定 |
| `export.js` | 進行中ラウンドの JSON 書き出し・共有 |

設計原則（2026-11-14 障害の教訓）:
- 保存は「書いたら読み戻して照合」。失敗は握りつぶさず、警告バナーを出し続ける
- 検証関数は保存側ガード専用。復元の可否には使わない
- 同期完了処理は進行中ラウンドの状態・画面に干渉しない（キャッシュ差し替えのみ）
- 再描画は変更箇所周辺に限定。全量 JSON 化＋二重保存のような毎タップ処理を置かない
- Service Worker の新バージョンはラウンド進行中には有効化しない（次回起動時、ラウンドなしのときだけ差し替え）

## 3. GAS API 仕様（新規・最小）

- 方式: 現行踏襲の `doGet/doPost`＋`action` パラメータ。リクエストは CORS 回避のため `Content-Type: text/plain` で JSON 文字列を送る（現行の修正知見を継承）
- 応答: 常に JSON `{ ok: true, ... }` ／ 失敗時 `{ ok: false, error: "…" }`
- 認証なし・AccessLog なし（U-10）。デプロイ URL の秘匿のみで運用

| action | 方向 | 内容 |
|---|---|---|
| `getMaster` | GET | Courses 全件（コース名・サブコース・par/yard/hdcp・攻略テキスト）＋クラブマスタを返す。検証用コピーの Courses を正とする |
| `saveDraft` | POST | 進行中ラウンドの下書きを保存。保存先は検証用コピー内の専用シート「下書き」（1行保持: round_id / updated_at / payload_json）。PropertiesService の不可視な保存ではなく、目視確認できるシート保存にする |
| `getDraft` | GET | 最新の下書きを返す（18H 完走フィルターなし。日付形式はサーバー側で正規化） |
| `saveRound` | POST | 確定保存。Rounds シートへ既存形式で2行目に挿入（降順）。round_id は `R{yyyymmdd}_{courseId}`。ペイロードは holes_json / partners_json / game_json の既存キー構成と互換 |

- 実装しないもの: 分析取得（getAnalyticsData 相当）、アクセスログ、LINE 通知
- スコアカード（共有用）シートの描画は現行 GAS 側の責務だが、現行 Code.gs が未精査のため、検証用での扱い（簡易描画／後処理代替／省略）は実装初期に現行仕様を確認して決める（§9 残課題）

## 4. 画面構成

1. **ホーム**: 進行中ラウンドがあれば再開バナー／「新規ラウンド」／「復元」への導線。保存ステータスの要約（最終ローカル保存・最終下書き保存）
2. **ラウンド設定**: コース検索・選択、条件（日付・ティー・グリーン・天候・風）、同伴者（最大3名、過去の同伴者から選択可）
   - ゲーム設定（トモダチ使用時）: **打順シャッフル**ボタン＋**打順の手動設定**（並べ替え）オプション
   - **端末間復元オプション**: 「他の端末の下書きを引き継ぐ」を明示的に選んだ場合のみ getDraft を取得し、概要（コース・現在ホール・スコア概要）を確認してから引き継ぐ。自動では絶対に行わない
3. **ホール入力**: 本人＋同伴者を同一画面で入力（スコア／本人のパット・番手・FW・OB・ペナ・バンカー／同伴者のスコア）。ホールメモ。現在までの合計を常時表示。画面下部に保存ステータスを常設
4. **確認・終了**: 全ホール合計の確認 → 確定保存。オフライン時は保留キューに入り、復帰時に自動送信（状態はホームで可視化）
5. **復元**: 端末内（最新世代→前世代）→ クラウド下書きの順に候補を提示。各候補は概要付き。「データなし」と「不完全かもしれない」を分けて表示し、不完全でも本人の判断で復元できる
6. **状態・設定**: 最終ローカル保存時刻／最終クラウド下書き保存時刻／ストレージ使用量／JSON エクスポート／マスタ手動同期

## 5. データモデル

- IndexedDB ストア: `meta`（設定・保存ステータス）、`master`（コースマスタキャッシュ）、`round`（進行中ラウンド。世代キーで最低2世代保持）、`pending`（確定保存の保留キュー）
- 進行中ラウンドの状態 JSON は、保存時にそのまま holes_json / partners_json / game_json へ写像できる形に保つ（後方互換 P7）
- 世代ローテーションはホール確定時。新しい保存が前世代を即座に潰さない

## 6. 保存・同期シーケンス

- 入力 → state 更新 → 300ms デバウンスで IndexedDB 保存 → 読み戻し照合 → ステータス更新。ホール移動・visibilitychange・pagehide で即時フラッシュ
- クラウド下書き: ホール確定時＋スコア変更時（デバウンス）に saveDraft。fetch はタイムアウト10秒、指数バックオフ最大3回。失敗しても入力とローカル保存は止めない（ステータスにだけ残す）
- マスタ同期: 起動時または手動。進行中はキャッシュ差し替えのみで画面に触れない
- 起動時: `navigator.storage.persist()` を要求

## 7. 失敗時の挙動（要点）

- ローカル保存失敗 → 警告バナー常駐＋再試行。容量超過時は進行中ラウンドを最優先で守り、コースマスタキャッシュはラウンド中に自動削除しない
- 下書き取得で「別端末の新しい下書き」を見つけても、端末間復元オプション未選択なら何もしない（提示もしない）
- 確定保存の応答不明（送信済みか不明）→ 保留キューに残し、round_id の重複チェックをサーバー側で行ってから再送する（二重登録防止）

## 8. テスト観点（移行計画・段階1の失敗再現への対応）

1. 序盤（スコア未入力・同伴者未登録）での強制終了 → 保護バックアップから再開できる
2. 同伴者スコアのみ入力した状態での再読込 → スコアが消えない（2026-11-14 の直接原因の再現テスト）
3. 弱電波を模した遅延下でのマスタ同期完了 → 進行中ラウンドの状態・画面が変わらない
4. ストレージ容量を圧迫した状態での保存 → 失敗がバナーで見え、ラウンドデータが守られる
5. 端末間復元オプション経由の引き継ぎ → 概要確認なしには上書きされない

## 9. 残課題

- スコアカード（共有用）描画の検証用での扱い（現行 Code.gs の仕様確認が先）
- GAS デプロイ手順の確立（初回デプロイ＋承認は本人の操作。以後の更新は既存デプロイの差し替えで URL を変えない）
- アイコン・manifest の MyGolf 用意（U-6）
