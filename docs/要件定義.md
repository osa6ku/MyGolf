## 1. 目的と前提

### 1.1 目的

2026-11-14の中津川CCラウンドで、現行MyScore（v1.0.53）がラウンド中にフリーズし、バックアップ復元も失敗した。精査の結果、障害は単発バグではなく構造に起因することが判明した。

- 永続化が localStorage のみで、保存失敗が例外の握りつぶしにより**無言化**されていた
- 復元処理の中にスコアを 0 に書き換えるコードがあり、**同伴者のスコアが復元のたびに消去**されていた
- 「データが無い」と「検証で弾かれた」を区別せず、実在するデータを「ありません」と表示した
- 1タップごとに全量保存が2回走る・マスター同期完了時に大規模DOM再構築が走る等、弱電波＋ラウンド中という実利用条件に合わない処理が残っていた

v1.0.54 / v1.0.55 で応急・恒久対策が順次入っているが（引継書 §4〜§6）、単一ファイル約14,900行の構造自体は残る。本プロジェクトは、**バックエンド（GAS＋マイスコア_DB_v1）をそのまま転用し、フロントエンドだけを正しい構造で新規開発**することで、同じ障害クラスを構造的に排除することを目的とする。

### 1.2 確定前提（ユーザー決定済み）

| # | 前提 | 内容 |
|---|---|---|
| P1 | DB転用 | バックエンドは既存の GAS＋「マイスコア_DB_v1」をそのまま使う。新アプリは既存データ（全ラウンド履歴・コースマスタ）を読み書きできること |
| P2 | デュアル記録 | スコア記録は新アプリ、ショット記録は Garmin Venu X1 が担当する。役割を混ぜない |
| P3 | GPSなし | スマートフォンのGPS計測機能は持たない（精度が実用にならないため廃止決定済み。現行でも v1.0.55 で撤去済み） |
| P4 | ライブ連携なし | アプリと Venu X1 の間ではラウンド中のリアルタイム連携を行わない（詳細は §3） |
| P5 | 同伴者対応 | 同伴者（最大3名、本人と合わせて4名）のスコアも入力できること |
| P6 | 保存の信頼性が最優先 | 保存失敗を無言で飲み込まない。失敗は必ず画面に出す。バックアップは世代管理する |
| P7 | ラウンド中の通信は最小限 | ゴルフ場の弱電波環境が前提。通信が UI を止めてはならない。マスター同期がラウンド開始直後に走って画面を固めないこと |
| P8 | 解析は後処理 | 解析・レビュー生成はラウンド後の後処理（Muse担当）の責務であり、アプリ本体の必須機能ではない |

### 1.3 利用者・利用環境

- 利用者: 本人（左打ちゴルファー）＋同伴者最大3名のスコアを本人が入力する運用
- 端末: iPhone（ホーム画面に追加した PWA として起動）。将来の Android 利用は必須としない
- 環境: ゴルフ場（弱電波・圏外がありうる）、片手・屋外での素早い入力が中心。ラウンド中に長文入力や複雑な操作を求めない

## 2. 機能要件

要件には優先度を付す。**必須** = 初期リリースに含める／**推奨** = 初期リリースに含めることが望ましい／**任意** = 後処理または将来対応でもよい。

### 2.1 ラウンド前

| ID | 要件 | 優先度 |
|---|---|---|
| F-PRE-1 | コース選択: 既存 Courses マスタ（全国3,038コース）から検索・選択できる。選択時にサブコース（OUT/IN等）・パー・ハンディキャップ・ヤーデージ・ホール攻略テキストを読み込む | 必須 |
| F-PRE-2 | ラウンド条件の設定: 日付、ティー、グリーン、天候、風を記録できる（既存 Rounds カラムに対応） | 必須 |
| F-PRE-3 | 同伴者登録: 同伴者の名前を最大3名まで設定できる。過去の同伴者から選べることが望ましい | 必須 |
| F-PRE-4 | ラウンド開始時点で進行中ラウンドのスナップショットを作成し、保護バックアップの対象とする（スコア未入力・同伴者未登録の状態でも「進行中」として扱う。現行 v1.0.53 で序盤にバックアップが作られなかった問題の再発防止） | 必須 |
| F-PRE-5 | マスター同期はラウンド開始前に明示的に行えること。開始後に裏で完了しても、進行中ラウンドの状態・画面に一切干渉しない（§2.7、N-4） | 必須 |
| F-PRE-6 | トモダチゲームを使う場合は、打順（initial_order）を設定できる（既存 game_json 形式に対応）。**打順シャッフル機能を搭載し、打順の手動設定もオプションとして選べる**（U-12 決定 2026-11-15） | 必須 |

### 2.2 ラウンド中（スコア入力）

| ID | 要件 | 優先度 |
|---|---|---|
| F-IN-1 | ホール単位の入力: スコア、パット数（本人のみ必須・同伴者は任意）、FWキープ（S/L/R/K/-）、OB、ペナルティ、バンカー回数を入力できる（既存 holes_json のキー構成に対応：pars / yards / hdcp / scores / putts / fw / clubs / ob / pen / bunker / shots） | 必須 |
| F-IN-2 | 本人の番手記録（使用クラブの並び）を入力できる。クラブ表記は既存マスタの表記・並び順（長い順：1W → 3W → 5W → 3H → 5H → 6I〜9I → PW → 度数ウェッジ → ChipR → PT）に統一する | 必須 |
| F-IN-3 | ホールメモ（フリーテキスト）を入力できる | 必須 |
| F-IN-4 | 入力はタップ中心で完結し、1操作の応答が体感で止まらないこと。再描画は変更箇所周辺に限定し、画面全体の再構築を毎タップ行わない（N-3） | 必須 |
| F-IN-5 | 保存は入力のたびに確実に行われるが、UIスレッドを塞がない方式とする（デバウンス＋ホール移動・画面非表示時の即時フラッシュ。現行 v1.0.55 の方針を継承） | 必須 |
| F-IN-6 | ホール移動（前へ／次へ）が常時可能で、移動確定時に「1ホール前の確定状態」を世代バックアップへ回す（§2.6） | 必須 |
| F-IN-7 | ニアピン等のゲーム記録（game_json の nearpin 等）を記録できる | 推奨 |
| F-IN-8 | 入力途中のホールでも、現在までの合計スコア・パット数がその場で確認できる | 必須 |
| F-IN-9 | GPS 計測・位置情報要求は一切行わない（P3） | 必須 |

### 2.3 ラウンド後

| ID | 要件 | 優先度 |
|---|---|---|
| F-POST-1 | ラウンド終了処理: 確定データを既存 GAS API 経由で Rounds シートへ保存する（最新ラウンドが2行目に入る降順構造、round_id 形式 `R{yyyymmdd}_{courseId}` を含め既存形式を踏襲） | 必須 |
| F-POST-2 | オフラインで終了した場合は保留ペイロードとして端末に保持し、オンライン復帰時に自動送信する（現行 `MyScore_v1_PendingRound` 相当） | 必須 |
| F-POST-3 | スコアカード（共有用）シートへの描画は現行どおり GAS 側で行われる前提とし、新アプリはその前提を壊さない形式で保存する | 必須 |
| F-POST-4 | ~~完走時の LINE 通知~~ **対象外（U-8 決定 2026-11-15: 不要のため実装しない）** | — |
| F-POST-5 | ラウンド確定データを、後処理（Garmin連携レビュー、§3）で参照できる形で DB に残す。新アプリ側でレビュー生成は行わない（P8） | 必須 |

### 2.4 マスタ管理

| ID | 要件 | 優先度 |
|---|---|---|
| F-MST-1 | コースマスタは既存 Courses シートを正とし、アプリはキャッシュとして保持する。キャッシュ形式は端末ストレージを圧迫しないこと（現行は 3,038 コース分を localStorage に同居させ容量圧迫の一因だった） | 必須 |
| F-MST-2 | マスター同期の完了処理は、ラウンド進行中はキャッシュ差し替えのみとし、画面再描画を行わない。選択肢等の再描画は設定・コース選択画面を開いた時点で行う | 必須 |
| F-MST-3 | 攻略テキスト（Courses.sub_courses_json の hole_strategies）はラウンド中のホール画面で参照できる | 推奨 |
| F-MST-4 | クラブマスタ（表記・並び順）は既存の統一済み表記を正とする。架空クラブの混入（過去の「6U」事例）を防ぐため、クラブはマスタからの選択式を基本とし、自由入力は例外扱いとする | 推奨 |

### 2.5 同伴者対応

| ID | 要件 | 優先度 |
|---|---|---|
| F-PRT-1 | 同伴者のスコアを本人と同じホール画面で入力できる。同伴者にはパット入力 UI が無くてもよいが、**パット未入力を理由にスコアが消去・無効化されることは絶対にない**こと（2026-11-14 障害の直接原因。再発防止を最重要要件とする） | 必須 |
| F-PRT-2 | 保存形式は既存 partners_json（`partner_id` / `name` / `scores[18]` / `putts[18]`（null 可）/ `total_score` / `total_putts`）と互換であること | 必須 |
| F-PRT-3 | 復元・再読込・同期のいかなる経路でも、入力済みの同伴者スコアが書き換えられないこと。「復元時にデータを正規化して書き換える」処理自体を置かない（§5） | 必須 |
| F-PRT-4 | 同伴者の合計スコアがその場で確認できる | 必須 |

### 2.6 バックアップ・復元

2026-11-14 障害の教訓をそのまま要件化する。すべて**必須**。

| ID | 要件 |
|---|---|
| F-BAK-1 | **保存失敗の可視化**: 書き込みは直後に読み戻して照合する。失敗したら画面上部に警告バナーを出し続ける。例外を握りつぶして正常に見せる実装を禁止する |
| F-BAK-2 | **「無い」と「不完全」を分ける**: 復元画面は、データが存在すれば検証結果によらず「保存データが見つかりました（不完全な可能性があります）」と概要（コース名・現在ホール・スコア概要）を提示し、本人の判断で復元できる。検証関数は保存側のガード専用とし、復元の可否判定に使わない |
| F-BAK-3 | **世代管理**: 進行中ラウンドの保存は最低2世代を保持し、新しい保存が前世代を即座に潰さない。ホール確定ごとに1世代ローテーションする（現行 v1.0.55 の `golf_prev_hole_backup` 方針を正式要件化） |
| F-BAK-4 | **クラウド下書き**: ホール確定時およびスコア変更時に GAS へ下書き保存する。取得は専用 API（現行 `getLatestOngoingDraft`、18H完走フィルターなし、日付形式を正規化）を用いる。通信はタイムアウト（目安10秒）＋上限付きリトライ（指数バックオフ、最大3回）とし、失敗しても入力・ローカル保存を止めない |
| F-BAK-5 | **復元の優先順位**: 端末内データ（最新世代→前世代）→ クラウド下書き、の順に提示する。**端末間復元は自動では行わず、ラウンド設定のオプションとして明示的に選択した場合にのみ、他端末のクラウド下書きを引き継げる**（U-7 決定 2026-11-15。白紙上書き事故は「自動でやらない」ことで防ぐ） |
| F-BAK-6 | **端末外エクスポート**: 進行中ラウンドを JSON ファイルとして書き出し・共有できるボタンを常備する（共有シート／ファイル保存）。端末ストレージが全滅した場合の最終退避経路とする |
| F-BAK-7 | **保存ステータスの表示**: 設定画面に「最終ローカル保存時刻」「最終クラウド下書き保存時刻」「ストレージ使用量概算」を表示し、保存が正常かを本人が目視確認できる |
| F-BAK-8 | 起動時に `navigator.storage.persist()` を要求し、OS の自動整理による消去リスクを下げる |
| F-BAK-9 | 容量超過時は、進行中ラウンドデータを最優先で守る。自動削除の対象は分析キャッシュまでに留め、コースマスタキャッシュはラウンド中に自動削除しない（弱電波の現場で再取得できないため。v1.0.55 の方針を継承） |

### 2.7 起動・同期の振る舞い

| ID | 要件 | 優先度 |
|---|---|---|
| F-SYN-1 | 起動時に進行中ラウンドがあれば、そのまま再開できる。再開時にデータ内容を書き換える処理（正規化・補完・消去）を一切行わない | 必須 |
| F-SYN-2 | バックグラウンド同期（マスタ・分析データ）は起動直後に走ってもよいが、完了処理が進行中ラウンドの状態を初期化・上書きすることは決してない。同期結果はキャッシュ保存のみ | 必須 |
| F-SYN-3 | 分析データ（過去ラウンド履歴）の取得・表示はラウンド記録とは分離し、その失敗・遅延がスコア入力に影響しない | 必須 |

## 3. Garmin Venu X1 連携

### 3.1 役割分担（確定前提）

| 対象 | 担当 | 内容 |
|---|---|---|
| スコア記録 | **新アプリ** | 本人＋同伴者のスコア、パット、FW、OB/ペナルティ/バンカー、番手の並び、ホールメモ |
| ショット記録 | **Venu X1** | AutoShot によるショット検出＋ Club Prompt（クラブトラッキング）でのショット後クラブ選択。コースデータは時計内蔵の 43,000+ コースプリロードを使用し、端末側へのコースダウンロードは不要 |
| 解析・レビュー | **ラウンド後の後処理（Muse）** | 両データをマージしてレビューを生成（§3.3）。アプリ本体の機能ではない（P8） |

- **ライブ連携はしない**（P4）。ラウンド中にアプリと時計が通信することは要件に含めない。連携点は「ラウンド後にデータを突き合わせる」1点のみ。
- 時計側の運用前提: 左打ちのため AutoShot の検出条件に合う装着（利き腕と逆側＝右腕）が推奨されること、Club Prompt はショットの後に使ったクラブを選択する操作であること、選択漏れのショットも記録自体は残り Garmin Golf アプリで後から修正できることは、アプリではなく運用ガイド側の周知事項とする。

### 3.2 ラウンド後のデータ取り込み

| ID | 要件 | 優先度 |
|---|---|---|
| F-GRM-1 | 取り込み経路: Garmin の **FIT ファイル**（時計を USB 接続して GARMIN/ACTIVITY フォルダから取得、または Garmin Connect の「オリジナルをエクスポート」）を後処理で取り込めること | 必須 |
| F-GRM-2 | 取り込んだ FIT のショット記録と、その日の新アプリのスコア記録（Rounds の該当 round_id）を **日付＋コースで突き合わせ**、ホール単位でマージできること | 必須 |
| F-GRM-3 | マージ結果はレビュー生成（§3.3）の入力とする。マージ処理自体は後処理側の責務であり、新アプリは「確定済みスコアデータを DB から参照できる」ことで連携する（F-POST-5） | 必須 |
| F-GRM-4 | FIT の読み取り仕様は 2026-11-15 に実データで検証済み：スコアカードはアクティビティとは別ファイルで時計の GARMIN/SCORCRDS フォルダにあり、ショット座標・クラブID・ピン位置を含む（構造の実測記録は Review #1 §12）。パット数はスコアカードに含まれないため、パットの正はアプリ記録とする。未決事項 U-9 はこれで実質解消 | 必須 |

### 3.3 レビュー生成（Review 形式）

後処理で生成するレビューの最低構成（パイロット = Review #1）:

1. **クラブ別実測飛距離表**: Venu X1 のショットデータからクラブごとの実測飛距離（平均・最大・本数）を集計
2. **ホール別履歴**: そのコースの過去ラウンド（マイスコア_DB の履歴）とのホール単位の比較
3. **スコア分解**: スコア・パット・FWキープ率・OB/ペナルティ/バンカー（アプリ記録）とショット傾向（Garmin記録）の突き合わせ
4. **ショットマップ**（2026-11-15 追加、本人が試作を承認）: スコアカードFITのショット座標（開始・終了）とピン位置から、ホールごとのショットマップを生成する。背景は衛星写真（Garmin独自のコース図形データはFITに含まれないため）。ショット線に番手と飛距離（GPS直線距離）のラベルを付け、スコア・パットはアプリ記録（正）を併記する。時計のタップ番手とアプリの打順記録が食い違う場合はフラグして本人確認に回す（誤タップがあり得る。2026-11-15 中津川H10の 54°/6I 事例で確定した運用）。AutoShot未検出のショットは座標が無く描けないことを明示する

### 3.4 分割データへの対応（2026-11-14 の実体験に基づく必須要件）

2026-11-14 の中津川CCでは、ハーフ終了時にラウンドを「一時休止」した後、正しい再開手順を取らず新規ラウンドとして開始したため、**Garmin データが前半・後半の2つに分割**された。後処理では以下を扱えること。すべて後処理側の要件だが、新アプリの確定データが突き合わせの基準になるため本章に明記する。

| ID | 要件 | 優先度 |
|---|---|---|
| F-GRM-5 | **分割データの結合**: 同日・同コースの複数の FIT ファイルを時系列につないで1ラウンド分として扱えること（前半＋後半の結合が代表ケース） | 必須 |
| F-GRM-6 | **欠け・重複の検出**: 取り込み・マージ時に、記録のないホール（欠け）と、同一ホールへの二重記録（重複）を検出して一覧で提示すること。黙って上書き・欠落させない（保存信頼性の方針 P6 と同旨） | 必須 |

## 4. 非機能要件

| ID | 分類 | 要件 |
|---|---|---|
| N-1 | オフライン耐性 | スコア入力・保存・復元（端末内）は完全オフラインで動作する。圏外であることがエラー表示や処理停止の理由にならない。通信を使う処理（マスタ同期・分析取得・クラウド下書き）はすべて「裏で・失敗しても入力に影響しない」設計とする |
| N-2 | 保存の可視化 | 保存の成否は常に本人が確認できる（F-BAK-1, F-BAK-7）。「保存したつもりで保存できていない」状態を構造的に作らない |
| N-3 | 性能 | スコア入力のタップ応答は即時（体感での引っかかりなし）。全量 JSON 化＋同期書き込みのような重い処理をタップのたびに実行しない。再描画は差分に限定する。初期ロードは現行（811KB 単一ファイル＋重い CDN ライブラリ）より軽くし、弱電波での再読込に耐える |
| N-4 | 割り込み耐性 | アプリ終了・タスクキル・端末再起動・ブラウザの強制リロードの後でも、最後に保存された状態から再開できる。sessionStorage / window.name のような揮発性の仕組みを恒久対策として数えない |
| N-5 | iPhone PWA の制約への対処 | (a) オリジンが異なるとストレージが別物になるため、配信 URL（オリジン）は1つに固定し、タブ版とホーム画面版で URL が割れないようにする (b) localStorage の上限（目安5MB級）に進行中ラウンドを依存させない。永続化の主軸は IndexedDB とし、大容量キャッシュと進行中データを分離する (c) `navigator.storage.persist()` を要求する (d) Service Worker のキャッシュ更新で旧版と新版が混在しないよう、版管理と更新手順を決める |
| N-6 | データ保全 | 過去データ（Rounds の全履歴）は読み取り互換を維持し、新アプリの不具合で既存行を書き換えない。書き込みは新規ラウンドの追加と下書き領域に限定する |
| N-7 | 表示・操作性 | 屋外の日差しの下で読めるコントラスト、大きめのタップ領域、片手操作を前提とする。本人の入力（スコア＋パット）と同伴者の入力が一目で区別できること |
| N-8 | セキュリティ | **認証なし・AccessLog なし（U-10 決定 2026-11-15）**。GAS のデプロイ URL は推測困難なものとし、URL の管理は本人が行う。検証用コピーには本人のスコアデータのみが入り、認証省略のリスクは本人が受容済み |
